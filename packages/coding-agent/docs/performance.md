# 性能与能力基线

这里记录可复跑的速度数据和能力数量。速度只比较同一机器、同一源码和同一配置下的结果；能力数量用于防止后续改动无意中删掉功能。

## 结论

2026-08-10 的 Windows 实测结果：

| 场景 | 旧 `tsx` 中位数 | Node 原生中位数 | 节省时间 | 延迟降低 | 加速倍数 |
|---|---:|---:|---:|---:|---:|
| `pi-dev --version` | 0.194 秒 | 0.092 秒 | 0.102 秒 | 52.6% | 2.11 倍 |
| RPC 可用 | 6.165 秒 | 2.031 秒 | 4.134 秒 | 67.1% | 3.03 倍 |

P95 表示 95% 的样本不超过该耗时：

| 场景 | 旧 `tsx` P95 | Node 原生 P95 | 节省时间 | 延迟降低 |
|---|---:|---:|---:|---:|
| `pi-dev --version` | 0.211 秒 | 0.124 秒 | 0.087 秒 | 41.1% |
| RPC 可用 | 7.438 秒 | 2.374 秒 | 5.064 秒 | 68.1% |

完整 Agent 初始化的主要指标是 RPC 可用时间：日常 `pi-dev` 把它降到旧路径的约三分之一。`--version` 因为现在会在加载 Agent 主体前直接返回，已经进入百毫秒级。Node 原生路径仍直接执行源码，不依赖可能过期的 `dist`。

## 本轮内部阶段变化

本轮优化进行中曾在扩展按需加载落地前记录一份阶段样本。Node 原生 `--version` 中位数从 1.946 秒降到最终的 0.092 秒，减少 95.3%，约快 21.1 倍。RPC 从 1.890 秒变为 2.031 秒，相差 0.142 秒；7 个样本不足以把这 7.5% 差异判断为稳定退化或提升。

这说明按需加载主要消除了版本、帮助等短命令不需要的模块加载；完整 RPC 仍然需要初始化 Agent。阶段样本保存在 [按需加载前基准](benchmarks/2026-08-10-windows-before-lazy-loader.json)，只用于解释本轮变化，不作为干净提交间的正式对比。

## 测量方法

- 系统：Windows `10.0.26200` x64
- CPU：Intel Core Ultra 7 255HX，20 个逻辑处理器
- 内存：约 31.5 GiB
- Node：v24.13.1
- 源码基点：`a26e6c709897192e4f15b2651062397349ac5064` 加当时未提交的能力平台改动
- 每个场景先预热 1 次，再测量 7 次
- `tsx` 和 Node 原生执行交错运行，避免固定顺序偏差
- 使用同一个临时配置目录，强制离线并关闭版本检查
- `version` 测到进程正常退出；RPC 测到真实 `get_state` 成功响应
- 没有模型调用、网络请求或 API token 消耗

7 个样本适合记录本机开发体验，不是发布级服务 SLA。最终原始样本保存在 [2026-08-10 Windows 基准](benchmarks/2026-08-10-windows-pi-dev.json)。

复跑命令：

```powershell
npm run benchmark:pi-dev -- --runs 7 --warmup 1 --mode all --output packages/coding-agent/docs/benchmarks/local-pi-dev.json
```

## 尚未声称的指标

- 没有把原生文件搜索宣称为比 `rg` 更快。它的首要收益是 Windows 没有 WSL/Git Bash/`rg` 时仍然可用；后续应在固定语料库上单独测量延迟和召回率。
- 没有给 LSP、DAP、网页、PDF 或远端 MCP 写统一延迟数字。这些结果主要由语言服务器、调试适配器、文件大小和网络决定，混成一个平均值会误导。
- MCP 的“后台发现”是启动路径约束，不代表远端服务本身没有延迟。远端调用仍受各服务超时控制。

任何后续性能结论都应保留原始样本、机器信息、源码版本和测量命令，不能只写一个百分比。
