# ADR 0020：强权限必须在工具进程之外执行

- 状态：Proposed
- 日期：2026-08-09
- 影响范围：coding-agent 的工具、扩展、审批、RPC、凭据、沙箱和审计

## 背景

Pi 当前运行在本地用户权限下。加载到同一 Node.js 进程的扩展可以绕过工具包装器，直接调用文件系统、网络和子进程 API。因此，给工具增加风险等级和能力清单可以改善审批与审计，但不能形成针对恶意或已被攻破扩展的安全边界。

如果界面把这种声明描述为“已沙箱化”，用户会产生比没有安全功能更危险的错误信任。

## 决策

1. `CapabilityManifest` 描述工具可能使用的能力，每次调用再根据实际参数生成动态能力请求。
2. 策略引擎位于工具调用路径之外，TUI、JSON、RPC 和无人值守模式共享同一判断结果。
3. 权限、审批、评分器、稳定版本指针和审计属于控制面，存放在工作区外；数据面不能修改。
4. 任何同进程扩展都明确标记为“受信代码”；能力规则对它们属于协作约束，不宣称能阻止恶意行为。未受信的第三方扩展不能加载进主进程。
5. 需要强制边界的第三方工具、扩展和候选在受控子进程、容器、虚拟机或操作系统沙箱内执行。
6. 凭据由进程外代理按目标来源和动作临时提供，不能复制全部环境变量。
7. UI 对每项能力显示“提示级”或“已强制”，并展示实际路径、命令、域名、凭据和批准范围。
8. RPC 只有经过本地会话授权的调用方可以批准动作；远程监听默认关闭，启用后必须认证并防重放。
9. 无法可靠解析的 shell、路径或网络目标按更高风险处理；无人模式失败关闭。
10. 资源限制作用于整个进程树，覆盖超时、输出、CPU、内存、磁盘和进程数量。

## 原因

- 安全检查与被检查代码处于同一权限域时，恶意代码可以绕过检查。
- 动态能力请求能区分同一工具的普通读取和高风险联网执行。
- 明确“提示级/已强制”可以避免用户误把审批当沙箱。
- 控制面分离能阻止候选修改评测和批准自己的规则。

## 备选方案

### 方案 A：只使用工具名和 read/write/exec 三级风险

简单且便于操作，但 `bash`、LSP、eval 和浏览器都可能跨越多种能力，粒度不足，因此只保留为兼容和默认提示层。

### 方案 B：在 Node.js 内拦截 `fs`、`net` 和 `child_process`

覆盖不完整，原生模块、依赖和新 API 容易绕过，不作为安全边界。

### 方案 C：所有任务强制进入容器

边界最清晰，但安装成本、Windows 兼容和启动延迟较高，不适合作为唯一运行方式。严格与无人值守模式可以默认使用，普通本地模式需要明确风险提示。

## 结果

正面影响：

- 权限说明与实际保证一致。
- 高风险扩展和自进化候选有可执行的隔离边界。
- 所有模式共享相同策略，减少绕过路径。

代价：

- 需要维护跨平台进程和沙箱后端。
- 隔离启动会增加部分任务延迟。
- 某些语言服务器、调试器和项目工具需要额外挂载与配置。

## 约束

- 宿主机模式不能宣称防御当前用户权限下的恶意扩展。
- 仅把控制面文件放到工作区外并不构成隔离；强制模式还必须确保工具进程没有挂载、句柄或凭据可以访问它们。
- 审计完整性校验可以发现损坏；如果信任锚仍由同一用户控制，就不能宣称防御该用户篡改。
- 文件授权必须处理符号链接、junction、UNC、设备路径、大小写和检查后替换。
- 网络授权必须处理 DNS 重绑定、重定向、代理、本机地址、局域网和云元数据地址。
- 回滚只能恢复 Pi 的配置与本地候选，不能撤销已经发生的发布、删除、付费或外部 API 副作用。
