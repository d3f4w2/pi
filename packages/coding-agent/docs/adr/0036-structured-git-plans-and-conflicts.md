# ADR 0036：结构化提交计划与冲突解决

- 状态：Accepted
- 日期：2026-08-10
- 影响范围：coding-agent 的内置 `git` 工具

## 背景

内置 `git` 工具已经能查看、暂存、提交和推送，但有两个断点：

- 多组无关改动只能由 Agent 临时记住分组，无法证明文件是否遗漏、重复或形成依赖环。
- `overview` 能发现冲突，`diff` 却拒绝冲突文件，Agent 只能退回 shell 或直接编辑冲突标记。

例如，工作区同时修改实现、测试和文档时，错误的提交顺序可能让中间提交无法通过检查；`UU src/config.ts` 出现后，结构化工具又不能展示 base、ours 和 theirs。

## 决策

扩展现有单一 `git` 工具，不增加任意 Git 参数入口。

1. `plan_commits` 接收 Agent 提议的提交组与显式依赖，只做验证，不暂存或提交。
2. 每个当前变更必须恰好出现在一个组中；未知、遗漏、重复路径和依赖环全部拒绝。
3. 工具返回工作区版本摘要和拓扑排序后的执行顺序，后续仍使用现有 `stage` 与 `commit`。
4. `conflicts` 从 Git 索引的 stage 1/2/3 读取 base、ours、theirs，返回有界文本预览、索引版本指纹和工作树指纹。
5. `resolve_conflict` 支持整文件选择 `base`、`ours`、`theirs`，或把已经人工编辑的 `worktree` 标记为已解决。
6. 解决前重新读取索引并校验版本指纹；`worktree` 还必须校验当前内容指纹并拒绝残留冲突标记。
7. 选择索引版本时先原子替换工作树文件，再精确 `git add -- <path>`；暂存失败时恢复原工作树内容。
8. 解决动作始终进入用户确认，且只允许当前仓库内、Git 明确认定为冲突的普通文件。

## 结果

正面影响：

- Agent 能在写 Git 历史前证明提交计划完整且无环。
- 冲突处理继续复用同一个工具、路径边界和审批面，不需要 shell 或新的内部 URL 语法。
- 指纹阻止旧预览解决已经变化的冲突。

代价：

- 提交组之间的依赖由 Agent 显式声明；第一版不猜测源码依赖。
- 第一版只处理普通文本文件，二进制、子模块和符号链接冲突需要普通 Git 工具或人工处理。

## 备选方案

### 自动分析并直接拆分提交

自动化程度高，但启发式分组可能把用户改动拆错，而且一次调用会连续修改暂存区和历史，因此拒绝。

### 引入 `conflict://` 写协议

路径很短，但会给模型增加第二套写入语义。现有 `read`、`edit` 和 `git` 已能组成“查看变体、编辑、校验、暂存”的闭环，因此不增加协议。
