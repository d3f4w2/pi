# ADR 0026：回归测试必须通过本地证据质量门

- 状态：Accepted
- 日期：2026-08-09
- 影响范围：错误恢复追踪、回归候选校验、二次审批和批准记录

## 问题

“测试可以运行并通过”不代表测试有效。候选可以在测试文件里重新定义一个假的目标函数，再证明这个假函数符合预期；这种测试不触达产品代码，真实功能损坏时仍会保持绿色。

普通、预期内的工具错误也不一定代表产品缺陷。例如读取一个不存在的文件后正常报告 `ENOENT`，没有发生代码修复，不应该触发回归测试制作。

## 决策

在双重审批流程中增加两道完全本地的质量门：

```text
运行证据门
  失败发生
  → 后续修改代码
  → 后续验证通过
  → 才询问是否制作

候选证据门
  有测试框架和断言
  → 引用真实项目模块、包或 CLI
  → 没有只在测试内重建被测功能
  → 才展示二次审批
```

两道检查都不调用模型、不联网，也不读取 API Key。

## 运行证据

只有同一个待恢复失败之后同时观察到以下证据，才形成回归候选：

1. `edit`、`write`、`ast_edit` 或 LSP rename 成功修改需要验证的代码或配置。
2. 随后的 `verify` 或 LSP diagnostics 明确通过。
3. 代理以正常完成状态结束。

单独的工具错误、用户取消、验证豁免、只重试后成功或没有代码修改，都不会触发。

## 候选证据

候选必须同时具备：

- 可识别的测试框架入口。
- 可识别的断言或失败检查。
- 至少一个产品触达证据：相对源码导入、非测试框架包导入、项目 CLI/源码路径，或 Go 被测包调用。

只有测试框架导入、标准库和测试文件内部定义的假实现时，候选被拒绝且不进入第二次审批。

## 边界和取舍

- 质量门宁可漏掉证据不足的 case，也不积累永远绿色的假测试。
- 检查基于保守的静态证据，不声称证明测试语义完全正确。
- 不执行候选来决定是否写入；执行仍由用户在 `/evals` 中明确选择。
- 旧批准记录没有质量字段时继续可见，但标记为“未经过质量门”。

## 验收

- 读取不存在文件并正常结束不再触发制题提示。
- 失败、代码修改、验证通过的完整链路仍会触发。
- 自定义假函数加断言的候选在写入前被拒绝。
- 引用真实产品模块并包含断言的候选可以进入二次审批。
- 二次审批展示具体产品触达证据。
- 新批准记录保存质量证据，旧记录仍可读取。
