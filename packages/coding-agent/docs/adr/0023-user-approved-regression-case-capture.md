# ADR 0023：回归测试制作必须经过两次用户批准

- 状态：Accepted
- 日期：2026-08-09
- 影响范围：coding-agent 的代理事件、评测、工具暴露、本地测试文件和用户审批

## 问题

真实错误是最有价值的回归测试来源，但自动复制源码、生成测试或写入项目会带来隐私、误判和测试污染风险。代理也不能同时负责出题、批准和修改评分标准。

## 决策

采用“发现 → 制作授权 → 内存候选 → 加入授权 → 原子写入”的双重审批流程：

```text
已恢复的真实错误
  → 只展示脱敏摘要
  → 用户允许或拒绝制作
  → 临时启用内部 eval_case 工具
  → 代理仅使用已有上下文生成最小测试
  → 展示完整候选内容
  → 用户允许或拒绝加入
  → 只创建新的测试文件并记录来源
```

具体约束：

1. 只有“先出现错误、后确认任务恢复”的运行才会提示制题。
2. 第一次批准前不保存候选、不读取额外源码、不增加模型调用。
3. 制题期间只允许调用内部 `eval_case`；其他工具调用由扩展阻止。
4. 候选只存在于本次工具参数和内存中；第二次批准前不写磁盘。
5. 第二次确认展示错误类型、测试路径、复现步骤、预期结果和完整测试内容。
6. 只允许创建新的测试文件；禁止覆盖、绝对路径、目录越界和非测试路径。
7. 候选总内容限制为 4,000 个字符，最多两个文件，推动最小复现。
8. 密钥形态、私人密钥、用户绝对路径和危险控制字符会直接拒绝。
9. 多文件写入使用排他创建；任一文件或审计记录失败时回滚本轮新文件。
10. 用户可以拒绝本次制作，或持久屏蔽同类错误提示；不提供永久自动批准。
11. 无交互确认能力时默认拒绝。

## 为什么只处理“已经恢复”的错误

尚未修复的失败没有“修复后通过”的证据，直接保存容易把猜测固化为测试。代理可以暂存一个无内容的失败信号；只有同一会话后续正常完成或验证通过，才向用户提出制题建议。

## 为什么测试写入项目而不是评测控制目录

真正的回归测试应该跟随代码、接受 Git 审查并由项目现有测试框架运行。控制目录只保存来源、摘要、批准时间和文件哈希，不复制测试正文。

## 验收

- 未批准、拒绝或无 UI 时不会创建文件。
- 第一次批准前没有额外模型调用或工具 schema。
- 制题期间读取、联网和执行工具被阻止。
- 第二次确认前磁盘无候选文件。
- 越界、覆盖、秘密和控制字符测试通过。
- 部分写入失败会删除本轮创建的文件。
- 正式测试记录能够追溯到错误类型、工具、时间和用户批准。
