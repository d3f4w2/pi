# 精准测试影响分析

## 问题

修改 `shared/parser.ts` 时，真正受影响的测试可能叫 `user-api.test.ts`。只比较文件名会漏掉它；直接运行全部测试又可能很慢，还可能启动端到端测试或真实 API。

## 第一性原理

一个测试需要运行的根本原因是：它直接或间接依赖了被修改的代码。

```text
修改的文件
  ← 被哪些源码导入
  ← 这些源码又被哪些文件导入
  ← 找到测试文件
  → 只运行这些测试
```

这是一张临时的反向依赖图。它只保存文件路径和导入关系，不把源码交给模型，因此不消耗模型 Token。

## 实现结构

```text
extensions/verify/
├── impact.ts       文件枚举、导入解析、反向依赖图、测试排序
├── workspace.ts    项目识别、验证命令规划、影响分析接入
├── service.ts      顺序执行、超时、失败摘要和日志
└── types.ts        verify 请求与结果类型
```

`verify auto` 的流程：

```text
定位目标文件和包根目录
  → 运行静态类型检查
  → 在包内建立临时依赖图
  → 从目标文件反向广度优先查找测试
  → 合并原有文件名匹配结果
  → 最多运行 20 个测试文件
```

距离目标文件更近的测试排在前面；距离相同时按路径稳定排序。文件名匹配继续作为保守补充，避免项目使用特殊导入写法时完全失去结果。

## 语言支持

| 语言 | 影响分析方式 |
| --- | --- |
| TypeScript/JavaScript | TypeScript 官方模块解析器，支持相对导入、`tsconfig` 路径别名、`import`、`export from` 和常见 `require` |
| Python | 解析 `import`、`from ... import ...` 和相对导入，支持常见 `src/` 布局 |
| Go | 保留包级 `go test`；Go 本身以包作为可靠的最小编译与测试单位 |

底层按语言适配器分开，后续可以增加 Go 的跨包反向依赖分析，不需要改变 `verify` 工具协议。

## 性能和安全边界

- 只扫描当前包，不扫描整个仓库和依赖目录。
- 最多枚举 5000 个源码文件；超过后立即停止建图。
- 单个文件最多读取 512 KiB；超大文件跳过并提示分析不完整。
- 最多选择 20 个测试文件。
- 32 个文件一批读取，避免同时打开过多文件。
- 不执行源码，不启动 LSP，不联网，不写索引。
- 建图失败或超限时退回文件名匹配，绝不自动改为全量测试。

这些边界使影响分析保持为可选加速器：能快速确定就使用，不能确定就明确降级，不拖慢主任务。

## 已知边界

- 运行时拼接的模块名、插件注册和反射无法通过静态导入完全识别。
- Python 的动态导入无法可靠解析。
- 跨工作区包的影响默认不扩散，避免一次小改动触发整个 monorepo。

用户明确要求完整测试时，仍应使用 `verify` 的 `operation=test` 并把 `path` 指向项目目录。
