# 单代理执行闭环架构

## 目标

用最小的运行时和上下文成本，提高单代理完成代码任务的可靠性。

非功能目标：

- 普通问答和只读任务：零额外模型 token、零额外进程。
- 正常完成验证的代码任务：只执行常数时间的内存判断。
- 漏检任务：最多注入两条短消息，禁止无限循环。
- 可选验证能力不可用：快速放行，不阻塞任务。

## 数据流

```text
成功的写入工具
      ↓
记录 revision 和代码路径
      ↓
成功或失败的 verify/LSP
      ↓
记录对应 revision 的验证状态
      ↓
代理输出最终文本
      ↓
已验证 ── 是 ──→ 静默结束
   │
   否
   ↓
verify 已开启且未超过上限
      ↓
发送一次短 steer，继续当前代理循环
```

## 组件

### `policy.ts`

纯内存状态机，负责：

- 判断路径是否属于需要验证的代码或构建配置。
- 从工具事件中提取修改文件。
- 维护修改版本、验证版本、失败状态和提醒次数。
- 决定当前是否需要提醒。

它不依赖 UI、文件系统或进程，便于单元测试。

### `index.ts`

扩展适配层，负责：

- 在 `agent_start` 重置本次任务状态。
- 在 `tool_result` 把成功写入和验证结果交给状态机。
- 在没有工具调用的 `turn_end` 判断代理是否准备结束。
- 仅当 `verify` 当前已开启时发送短 `steer`。

## 状态不变量

1. `revision` 只在成功的相关代码修改后增加。
2. 只有发生在当前 `revision` 上的成功验证才有效。
3. 失败验证不能把修改标记为已验证。
4. 不可用或超时属于放行状态，不能触发重试循环。
5. 每个 `revision` 最多提醒一次，每次代理运行最多提醒两次。

## 性能与 token

每个工具结果只检查少量固定字段和文件后缀，时间复杂度为 `O(p)`，`p` 是单次工具报告的路径数，且会限制数量。状态只保存在内存中，不写磁盘。

扩展不注册模型可见工具，因此不会扩大每次请求的工具 schema。正常路径不发送消息，只有漏检时才产生额外 token。

## 失败模式

| 情况 | 处理 |
|---|---|
| 工具结果没有路径 | 忽略，不猜测 |
| 修改的是文档或图片 | 忽略 |
| `verify` 未开启 | 静默放行 |
| 验证工具不可用或超时 | 标记放行，不再提醒 |
| 代理忽略提醒 | 达到上限后结束 |
| 验证后再次修改 | 旧验证失效 |

## 后续扩展

状态机可以继续接入调试器、基准测试和运行记录，但这些能力应通过新的证据类型扩展，不能让控制器直接承担工具执行。
