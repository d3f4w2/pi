# 受控自进化

## 它解决什么问题

Agent 会从一次任务中恢复，但修复方法通常只留在当前对话里。下次遇到同类问题，可能再次走错路。

例子：

```text
第 1 次：bash 在 Windows 上失败 → 改用专用 grep → 完成
第 2 次：同类失败再次发生 → 改用专用 grep → 完成
```

这说明“先选专用工具”可能是一条有价值的策略，但两次成功恢复不等于它可以直接写进系统提示词。它仍可能只适合当前项目，或让其他任务变慢。

Pi-go 因此采用受控闭环：

```text
轻量记录 → 聚合同类信号 → 用户允许制案 → 候选冻结
    → 同模型、同案例 A/B 评测 → 用户批准灰度
    → 少量真实任务观察 → 用户正式启用或一键回滚
```

## 第一性原理

自进化不是“自己改代码”，而是三个能力的组合：

1. **提出假设**：从重复失败中提出一条最小行为改动。
2. **用证据选择**：旧行为和候选行为在同一隔离任务中比较。
3. **控制故障半径**：候选只能经过用户批准、小范围灰度和可逆切换后生效。

缺少第 1 点，只是在记录日志。缺少第 2 点，只是把模型的自我评价当事实。缺少第 3 点，则一次错误学习会污染之后的所有任务。

## 数据模型

### 信号

普通任务结束后只保存脱敏指标：任务类型、结果、失败工具、重试、验证状态、Token，以及标准化错误类别的不可逆 SHA-256。不会保存用户提示、源码、路径、命令、错误原文或工具输出。

同一项目中，相同指纹达到阈值后才成为“可学习信号”。一次偶发错误不会打扰用户。

### 候选

第一版支持两种候选：

- `prompt`：适用于该项目的短行为规则，每次任务都会注入。
- `strategy`：只有用户任务命中触发词时才注入。

候选包含来源信号、父候选、内容摘要、适用评测案例和状态。内容摘要使用 SHA-256；评测、批准和启用必须绑定同一个摘要。

### 生命周期

```text
proposed
   ↓ A/B 评测通过
evaluated
   ↓ 用户批准
canary
   ├─ 失败 → rolled_back
   └─ 达到观察次数 → awaiting_promotion
                         ├─ 用户启用 → promoted
                         └─ 用户拒绝 → rejected
```

稳定候选有父子谱系。新候选正式启用后，旧候选保留在历史中；回滚可以恢复上一稳定版本。

## A/B 评测为什么公平

基线和候选使用：

- 同一个模型和思考等级；
- 同一组启用工具；
- 相同隔离项目和隐藏验收规则；
- 相同超时、输出 Token 和工具调用预算。

区别只有附加的候选规则。系统记录成功、隐藏验收、预算、Token、延迟、工具调用和工具错误。确定性验收负责判定“能不能工作”，用户负责判断“是否更好”。

单次 A/B 只能作为小样本门禁，不能证明统计显著提升。因此候选还必须经过真实任务灰度，且最终启用仍由用户决定。

## 安全边界

- 默认不额外调用模型；只有用户允许制案或主动运行 A/B 时才产生模型消耗。
- 候选不能修改权限、审批、安全策略、依赖、安装脚本或工具能力。
- 候选不能包含疑似凭据。
- 候选生成期间只开放一次性内部提交工具，禁止读取文件、联网和执行命令。
- 评测运行在临时项目中，候选无法写评分器和隐藏验收文件。
- 灰度期只开放本地读取、搜索、编辑和验证工具；终端、Git 推送、浏览器和其他扩大故障范围的工具会被阻止。
- 灰度运行失败时自动停用候选；正式启用前仍需用户确认。
- 核心源码自修改属于 L5，当前明确不实现。

## 使用

输入 `/learn`：

- 查看重复失败和候选状态；
- 对候选运行隔离 A/B；
- 批准灰度；
- 正式启用；
- 回滚当前行为；
- 暂停或恢复自动观察。

平时无需手动整理日志。达到阈值时，Pi-go 会先说明发现了什么，再询问是否花一次模型调用制作候选。

## 性能成本

普通任务热路径只做一次内存判断和一次小型 JSON 事务，不调用模型。没有活跃候选时，不修改系统提示词。活跃候选有严格长度上限，避免上下文持续膨胀。
