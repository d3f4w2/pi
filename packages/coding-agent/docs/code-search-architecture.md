# code_search 架构与关键决策

本文记录内置 `code_search` 的职责、运行流程和关键取舍。使用方法见 [code-search.md](code-search.md)。

## 设计目标

`code_search` 同时满足以下目标：

- 不知道准确名称时，可以按功能意图找到相关代码。
- 普通项目尽量完整索引，保留跨目录关系和召回率。
- 大项目不能无限上传、等待或重复失败。
- 语义搜索不能拖慢不需要它的普通任务。
- 失败回退不依赖 Bash、WSL 或外部 `rg`。

核心定位是：`code_search` 是可选加速器，不是代理工作的基础依赖。

## 工具路由

模型按成本从低到高选择方法：

```text
当前上下文够用
  └─ 直接回答
已知准确路径
  └─ read
已知符号、文字、报错或配置键
  └─ 内置 grep
路径、符号和关键词都未知，需要按意图探索
  └─ code_search
code_search 未就绪或失败
  └─ 立即回到内置 grep，不等待、不重试
```

这条边界很重要。语义搜索适合“登录流程如何串起来”，不适合“`apiKey` 在哪出现”或“读取这个已知文件”。

## 运行流程

```text
code_search(query, path?)
        ↓
选择索引范围并启动 mgrep watch
        ↓
前台最多等待 2 秒
        ├─ 尚未就绪：后台继续索引，本次返回 warming，让代理改用 grep
        └─ 已就绪：执行 mgrep search
                         ↓
                    最多等待 15 秒
                         ├─ 成功：返回最多 6/12/20 条结果
                         └─ 失败：记录失败，本次任务改用 grep
```

启动 watcher 本身也负责暴露“未安装”“未登录”“文件超限”等错误，因此不再额外执行一次 `mgrep --version`。这减少了一次无意义的子进程往返。

## 索引范围

第一次尝试从项目根目录索引。默认文件安全上限是 5000：

```text
项目文件未超限
  └─ 保留整库 watcher
项目文件超限
  ├─ 有明确 path：尝试该目录
  └─ 无明确 path：停止并回退 grep
指定目录仍超限
  └─ 记录失败，不再重复尝试同一范围
```

搜索参数 `path` 只能限制结果，不能缩小已经从根目录启动的 watcher。因此扩展必须同时管理“索引根目录”和“搜索路径”。

## 文件职责

| 文件 | 职责 |
|---|---|
| `extensions/code-search/index.ts` | 注册工具、定义参数、告诉模型什么时候使用及如何回退。 |
| `extensions/code-search/types.ts` | 定义 watcher、搜索请求、错误类型和结果详情。 |
| `extensions/code-search/process.ts` | 启动 mgrep、设置超时、清理输出并分类错误。 |
| `extensions/code-search/search.ts` | 管理索引范围、前台等待预算、后台 watcher、熔断和结果路径。 |
| `core/system-prompt.ts` | 要求准确搜索使用内置 `grep`，不通过 Bash 运行 `rg`。 |
| `extensions/tools/index.ts` | 开启工具时说明安装、上传范围和非阻塞行为。 |

## 会话状态

`CodeSearchService` 在一次 Pi 会话中保存：

- 当前 watcher、索引根目录和是否已经就绪。
- watcher 的启动 Promise，避免同一范围并发启动。
- 已发生文件超限的范围。
- mgrep 的终止性失败，避免后续任务重复浪费时间。

前台超时不是 watcher 失败。当前调用返回后，健康 watcher 仍在后台运行；准备完成后可以被后续调用复用。

## 关键决策

### ADR-001：语义搜索按需使用

决定：只有路径、符号和关键词都未知，而且需要按功能意图探索时才调用 `code_search`。

原因：准确查找使用 `grep` 更快、更稳定、输出更小。无条件语义搜索会增加等待、工具输出和 token 消耗。

### ADR-002：前台最多等待 2 秒

决定：首次索引超过 2 秒就返回 `warming`，watcher 留在后台继续。

原因：索引可能需要几十秒或数分钟，但当前任务通常可以用 `grep` 继续。辅助能力不应阻塞主流程。

### ADR-003：单次语义搜索最多等待 15 秒

决定：`mgrep search` 超过 15 秒时终止，并提示代理立即回退。

原因：一次搜索的潜在收益不足以支撑长时间停顿。失败后继续等待或马上重试通常只会重复成本。

### ADR-004：普通项目优先完整索引

决定：首次尝试项目根目录，不默认猜测子目录。

原因：完整索引能保留跨包、测试和文档关系，召回率更高。文件安全上限负责控制代价。

### ADR-005：默认安全上限为 5000

决定：向 `mgrep watch` 传入 5000，可由 `MGREP_MAX_FILE_COUNT` 覆盖。

原因：mgrep 原始默认值 1000 对中型仓库偏小；无限提高又会扩大上传量和等待时间。

### ADR-006：只按明确 path 缩小范围

决定：整库超限后，只使用调用方明确提供的 `path`，不根据关键词猜目录。

原因：猜错范围会安静地漏掉代码，降低召回率。没有可靠范围时应明确回退到 `grep`。

### ADR-007：失败后熔断

决定：文件超限按目录记录；其他终止性 mgrep 失败按会话记录。

原因：安装状态、登录状态、额度和文件数量通常不会在几秒内改变。重复调用只会拖慢任务。

### ADR-008：精确回退使用内置 grep

决定：`code_search` 不可用时，由代理直接调用 Pi 的内置 `grep`，不通过 Bash 运行 `rg`。

原因：内置工具会直接启动受控的 ripgrep 进程，跨平台运行，不依赖 Git Bash 或 WSL，也能稳定控制输出量。

实现约束：Bash 的工具简介不能把 `grep` 或 `rg` 宣传为适用场景；内置 `grep` 的说明必须明确它优先于 Shell 搜索。搜索多个目录时，代理应分别调用多次内置 `grep`，不能因为一个调用只接收一个 `path` 就改用 Bash。

### ADR-009：内置 grep 默认开启，关闭后不允许 Shell 绕过

决定：SDK 创建的新会话默认激活 `grep`。用户在 `/tools` 中关闭 `grep` 后，系统提示明确说明精确内容搜索不可用，不再建议 Bash `rg` 作为替代。

原因：工具路由只有在模型实际拿到 `grep` 工具时才会生效。旧默认只开启 `read、bash、edit、write`，导致模型即使看到回退设计也只能调用 Bash。另一方面，关闭工具代表用户撤销该能力，Bash 不应成为绕过工具开关的后门。

## 路径和输出

- 所有路径先解析为真实路径，并拒绝项目外路径。
- 子目录 watcher 返回的路径会补回子目录前缀，模型始终看到项目相对路径。
- 文件路径会使用父目录建立索引，但搜索仍限制到该文件。
- 搜索结果最多 200 行或 32 KB，避免大输出挤占上下文。
- 默认返回 6 条，证据不足时再扩大到 12、20。

## 测试要求

`test/code-search-extension.test.ts` 至少覆盖：

- 严格工具路由提示。
- 2 秒前台预算与后台 watcher 复用。
- 15 秒搜索回退提示。
- 文件上限默认值和环境变量覆盖。
- 整库超限后切换到明确子目录。
- 相同失败范围不会重复启动。
- 子目录结果恢复为项目相对路径。
- 安装、登录、额度、控制字符和进程清理。

`test/system-prompt.test.ts` 覆盖内置 `grep` 的直接回退规则；`test/tools-extension.test.ts` 覆盖开启时的上传、文件上限和非阻塞提示。

## 后续修改入口

- 调整 mgrep 命令、超时或错误识别：修改 `process.ts`。
- 调整等待预算、索引范围或熔断：修改 `search.ts`。
- 调整模型何时搜索、扩大结果或回退：修改 `index.ts`。
- 改变上传范围或默认上限：同步更新开启提示、使用文档、架构文档和测试。
