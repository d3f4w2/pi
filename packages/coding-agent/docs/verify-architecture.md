# verify 架构与关键决策

## 目标

把“修改代码后证明结果正确”变成稳定工具能力，避免模型反复猜命令、目录和 shell，同时控制时间和上下文开销。

## 第一性原理

```text
代码修改
    ↓
识别项目和最小工作区
    ↓
选择类型检查或相关测试
    ↓
直接启动验证程序
    ↓
通过：返回短摘要
失败：返回关键错误并保存日志
```

LSP 证明代码符合语法和类型规则；测试证明行为符合预期。`verify` 负责后者，并复用类型检查作为第一道快速门槛。

## 模块结构

```text
extensions/verify/
├── index.ts      工具参数、模型规则和注册
├── workspace.ts  项目识别、工作区定位和命令规划
├── process.ts    无 shell 的进程执行、超时、取消和输出捕获
├── service.ts    顺序执行、错误压缩、日志和最终结果
└── types.ts      请求、命令、结果和详情类型
```

## ADR-016：专用验证工具，不开放任意命令

决定：工具只接受 `auto`、`typecheck`、`test` 和 `lint`，不接受任意命令字符串。

原因：任意命令会让 `verify` 退化成第二个 bash，重新引入 shell 选择、命令注入、跨平台差异和超长输出。命令由项目标记、脚本名和语言适配器生成，并通过参数数组直接启动。

## ADR-017：auto 不擅自运行整个测试套件

决定：`auto` 先运行类型检查，再通过有界反向依赖图寻找间接受影响的测试，并把文件名匹配作为保守补充。找不到相关测试时明确说明，但不自动运行完整仓库测试。只有显式 `operation=test` 且目标为项目目录，才允许运行完整测试脚本。

原因：大型仓库的完整测试可能包含端到端测试、真实 API、凭据或长时间任务。默认验证必须快且可预测。

依赖分析只扫描当前包，最多读取 5000 个源码文件和每个文件 512 KiB，相关测试最多定位 20 个文件，并跳过依赖、构建和覆盖率目录。超过边界时立即退回文件名匹配，不升级为全量测试。

## ADR-018：缺失工具继续，真实失败停止

执行规则：

- 某个可选程序不存在：记录安装提示，继续后续检查。
- 检查返回失败：停止，避免建立在失败基础上继续消耗时间。
- 检查超时：终止进程树并停止本轮。
- 用户取消：立即终止并抛出取消结果。

这使 Python 没装 basedpyright 时仍能运行已有 pytest，同时不会掩盖真正的测试失败。

## ADR-019：上下文只保留证据

进程最多捕获 2 MB 输出。失败时：

- 优先提取包含文件位置、error、failed、assert、panic、TS 错误码的行。
- 模型上下文最多放入 40 行，每行最多 500 字符。
- 已捕获的完整输出写入 `verify-logs`，返回本地路径。

每项默认超时 60 秒，可配置 5–300 秒。检查严格顺序执行，前一项真实失败后不再启动下一项。

## 语言适配

| 语言 | 类型检查 | 测试 | lint |
| --- | --- | --- | --- |
| TypeScript/JavaScript | 项目 typecheck 脚本或 `tsc --noEmit` | package.json test | package.json lint |
| Python | basedpyright → pyright | `python -m pytest` | `ruff check` |
| Go | `go vet` | `go test` | `go vet` |

新增语言只需要扩展 `workspace.ts` 的项目标记和命令规划，不改变工具协议或执行器。

## ADR-020：验证意图优先于内容查看

决定：用户明确说“检查刚才的修改”“验证刚才的代码”时调用 `verify`，而不是只读取文件。只有明确要求查看内容时才使用 `read`。

独立 Python 文件可以直接根据 `.py` 扩展名识别，文件所在目录作为最小工作区，不强制要求 `pyproject.toml`。项目标记仍优先用于查找完整配置。独立文件先通过 `ast.parse` 做语法检查；它只读取源代码，不导入、不执行，也不生成 `.pyc` 文件。

原因：读取只能证明内容存在，不能证明类型和测试通过；但自动执行普通源文件可能产生副作用，因此独立文件只做静态检查，不直接运行。

调用边界：支持语言的检查不得退回终端重复实现。只有用户明确要求运行程序，而且 `verify` 已完成安全检查后，才允许通过终端执行普通源文件。
