# 智能上下文整理

Pi 会在每次请求模型之前，自动整理已经过时或重复的工具输出。

它不会删除会话记录。终端里看到的历史、恢复会话、导出记录和后续压缩，仍然保留原始内容。只有发送给模型的临时副本会变短。

## 会整理什么

- 同一个工具、同一组参数重复执行时，较早的大结果可以被新结果替代。
- 文件被 `edit` 或 `write` 成功修改后，修改前的 `read` 结果会标记为过期；重新读取后的新内容仍然完整保留。
- 很旧并且很大的唯一结果，会保留开头和结尾，省略中间内容。
- 小结果不会处理，因为省不了多少 Token。
- 可选的缓存保护可以只修改后面不超过指定 Token 数的结果，避免为了少量节省破坏更深的暖缓存前缀。
- 启用缓存保护后，同一工具和参数的精确重复结果可以在这段尾部内立即省略，即使它仍位于最近输出保护范围。

## 永远保留什么

- 最新约 4 万 Token 的未过期工具输出
- 启用缓存保护后，后面仍有超过配置 Token 数消息的深层结果
- 所有错误信息
- 图片结果
- Skill 内容
- `AGENTS.md` 和 `SKILL.md`
- 体积很小的结果

被整理的结果会留下简短说明，告诉代理为什么省略，以及需要精确内容时重新调用哪个工具。工具调用和结果仍然成对存在，不会破坏模型接口。

Pi 只识别结果明确成功的 `edit` 和 `write`。修改失败、路径不同、终端命令或未知工具都不会让旧读取失效，避免错误删掉仍有用的信息。已经被后续修改明确证明过期的读取会优先标记，即使它位于缓存保护区，因为正确性高于缓存命中。

## 配置

在 `~/.pi/agent/settings.json` 或项目 `.pi/settings.json` 中：

```json
{
  "contextPruning": {
    "enabled": true,
    "cacheWarmSuffixTokens": 0,
    "protectRecentTokens": 40000,
    "minimumSavingsTokens": 8000,
    "minimumResultTokens": 512,
    "previewCharacters": 320
  }
}
```

默认值 `0` 表示不限制改写深度。只有在目标服务商已经通过缓存用量实验验证收益后，才建议设置非零值；设置 `enabled: false` 可以完全关闭上下文整理。

## 和压缩的区别

- 智能上下文整理：本地完成，不调用模型，每次请求前处理重复工具输出。
- 会话压缩：接近模型上限时调用模型，把较早的整段对话总结成摘要。

两者配合使用：前者减少日常浪费，后者负责最终的上下文溢出保护。

## 性能参考

在一个模拟的 120 次读取循环中，原始上下文约 24.1 万 Token。配置 8000 Token 缓存保护时只修改 2 个结果、节省约 3936 Token，并把最深改写的后缀限制在约 6033 Token；关闭保护会节省约 21.3 万 Token，但最深改写会影响约 23.9 万 Token 的后缀。本机处理耗时约 1.08 毫秒和 0.64 毫秒。目标第三方 API 的三请求实验中，两种方案都读取了 5632 个缓存 Token，而启用保护多发送了 2927 个未缓存 Token，因此该保护保持默认关闭。
