# LSP 架构与关键决策

本文记录内置 `lsp` 工具的职责、运行流程和关键取舍。使用方法见 [lsp.md](lsp.md)。

## 设计目标

- TypeScript 和 JavaScript 安装 Pi 后直接可用。
- Python 和 Go 使用相同协议和输出格式，不复制工具实现。
- 查定义、引用、类型和错误时使用语言分析结果，不让模型根据文本猜测。
- 语言服务器按需启动并复用，不能拖慢不需要 LSP 的任务。
- 缺少服务器、启动失败或请求超时后立即回退到 `grep` 和 `read`。
- 自动诊断只检查本轮修改文件，并限制时间、文件数、结果数和反馈轮数。
- 重命名只能修改当前项目，写入前必须完整验证所有编辑。

## 整体结构

```text
主代理
  ↓ lsp(operation, path, ...)
扩展入口 index.ts
  ↓ 参数和工具路由
LspService
  ├─ 校验项目路径
  ├─ 解析符号位置
  ├─ 复用工作区客户端
  ├─ 压缩和格式化结果
  └─ 安全应用 rename
        ↓
语言适配器
  ├─ TypeScript / JavaScript
  ├─ Python
  └─ Go
        ↓
通用 LSP 客户端
  ↓ JSON-RPC over stdio
语言服务器进程
```

## 工具边界

```text
已知准确文字、报错或配置键
  └─ grep
只知道准确符号，不知道所在文件
  └─ grep 定位文件和行号，再调用 lsp
不知道名称，需要按功能意图探索
  └─ code_search
已知文件或符号，需要确认代码关系、类型或错误
  └─ lsp
lsp 不可用
  └─ 立即回到 grep + read，不等待、不重试
```

## 支持的操作

| 操作 | 作用 | 是否修改文件 |
|---|---|---|
| `definition` | 查定义 | 否 |
| `type_definition` | 查符号对应类型的定义 | 否 |
| `references` | 查引用 | 否 |
| `implementation` | 查接口或抽象成员的实现 | 否 |
| `hover` | 查类型、签名和简短说明 | 否 |
| `symbols` | 查看文件中的类、函数和变量 | 否 |
| `workspace_symbols` | 在当前语言工作区查符号 | 否 |
| `diagnostics` | 查看单文件错误；`path="*"` 时运行项目级检查 | 否 |
| `rename` | 按语言规则重命名符号 | 是 |
| `rename_file` | 移动文件并同步更新引用 | 是 |
| `code_actions` | 列出或明确应用 quick fix / refactor | 可选 |
| `status` | 查看已启动、就绪或失败的服务器 | 否 |
| `reload` | 清理失败缓存并重启一个或全部服务器 | 否 |
| `capabilities` | 查看服务器实际声明的能力 | 否 |
| `request` | 发送受控的高级 JSON-RPC 请求 | 由方法决定 |

位置统一对模型使用从 1 开始的行号和列号；协议内部转换为从 0 开始。调用方也可以提供准确 `symbol`，由服务在文件中解析位置。符号出现多次时返回候选行，不猜测目标。

## 语言适配器

适配器只负责四件事：识别文件、确定语言 id、寻找工作区根目录、提供启动命令。

| 语言 | 文件 | 根目录标记 | 服务器 |
|---|---|---|---|
| TypeScript / JavaScript | `.ts`、`.tsx`、`.js`、`.jsx`、`.mts`、`.cts`、`.mjs`、`.cjs` | `tsconfig.json`、`jsconfig.json`、`package.json` | npm、源码和普通 Bun 安装随 Pi 提供；独立 Bun 二进制使用 PATH 中的 `typescript-language-server` |
| Python | `.py`、`.pyi` | `pyproject.toml`、`uv.lock`、`requirements.txt`、`setup.cfg` | `basedpyright-langserver`，其次 `pyright-langserver`、`pylsp` |
| Go | `.go` | `go.work`、`go.mod` | `gopls` |

找不到标记文件时使用当前 Pi 工作目录。Python 和 Go 的服务器由用户或项目环境安装；缺失时返回一条可执行的安装命令。

## 项目级诊断

`diagnostics path="*"` 是 `lsp` 工具内的项目验证分支，不启动语言服务器：

```text
lsp diagnostics path="*"
  ↓ 只检查当前工作目录的项目标记
TypeScript / JavaScript → node <local-or-bundled-tsc> --noEmit --pretty false
Go module              → go build ./...
Go workspace           → go work edit -json → go build <每个项目内模块>/...
Python                  → basedpyright → 找不到时尝试 pyright
  ↓
固定命令 + shell:false + 20 秒超时 + 最多 50 行结果
```

识别顺序为 TypeScript、Go、Python；同一个目录同时包含多种标记时只运行第一个匹配项，避免一次工具调用暗中执行多套检查。命令参数全部由程序生成，不拼接用户输入，不使用 `npx`，也不自动安装依赖。`go.work` 中位于当前项目之外的模块不会自动构建。测试命令具有项目差异，继续由 `bash` 显式执行。

## 客户端生命周期

```text
第一次请求
  ↓
选择适配器和工作区
  ↓
启动服务器并 initialize
  ↓
打开或同步目标文件
  ↓
发送请求并返回结果

后续同工作区请求
  └─ 复用客户端

session_shutdown
  └─ shutdown → exit → 必要时终止进程
```

服务按照“语言 + 工作区根目录”保存客户端。启动失败属于会话级终止错误，同一目标不会马上重复启动。单次超时只取消当前请求；连接损坏时关闭客户端并让后续任务回退。

Python 和 Go 工作区第一次真正启动客户端前，会显示对应安装检查命令。提示与客户端复用使用同一个工作区键，因此同一会话不会在每次调用时重复刷屏。

## 自动诊断闭环

```text
edit / write / lsp rename 成功
  ↓ 记录修改文件，并在后台启动语言服务器、打开该文件
当前工具批次结束（turn_end）
  ├─ 冷启动仍在进行：本轮不等待，保留文件到下一回合
  └─ 服务已就绪：去重并筛选受支持语言
并行诊断最多 8 个文件，总等待最多 2500ms
  ├─ 无问题：不写入模型上下文
  ├─ 有问题：最多反馈 20 条，进入下一轮修复
  └─ 超时或失败：只给用户短提示，代理继续任务
        ↓
同一次代理运行最多反馈两轮
```

自动协调器只监听能准确给出修改路径的 `edit`、`write` 和 `lsp rename`。它不猜测 `bash` 是否修改了哪些文件，也不对整个项目做隐式扫描。检查结果可能包含修改文件原有的问题，因此反馈会要求代理判断问题是否由本次修改引入。

自动检查使用与手动 `lsp diagnostics` 相同的客户端和缓存。预热只启动服务并同步明确修改的文件，不生成模型消息。第一次回合遇到仍在启动的服务时，不消耗 2500ms 预算等待；服务在模型继续工作时完成启动，下一回合再执行正式诊断。第二次仍未就绪时才进入原有的有界等待和开放降级，避免无限延后。

## 安全重命名

`rename` 的返回值是一个 `WorkspaceEdit`。写盘前执行：

1. 拒绝非 `file:` URI 和项目外路径。
2. 拒绝创建、删除、移动文件等未支持的资源操作。
3. 读取所有目标文件并保存原内容。
4. 校验范围、重叠编辑和当前文件快照。
5. 在内存中从后向前应用每个文件的编辑。
6. 全部计算成功后才开始写盘。
7. 写入中途失败时恢复已经写入的原文件。
8. 通知语言服务器文档已经变化。

文件重命名使用 LSP 的 `workspace/willRenameFiles` 和 `workspace/didRenameFiles`。目标路径及其真实父目录都必须位于项目内，目标不能已存在；文件移动或引用写入失败时恢复旧路径。代码操作默认只列出候选，只有准确选择一项并进入写入确认后才应用。服务器在已确认的代码操作中发起 `workspace/applyEdit` 时，仍复用同一套项目边界、快照、重叠校验和回滚逻辑。

工具只返回修改文件、编辑数量和简短摘要。代理随后使用 Git diff 检查结果。

## 关键决策

### ADR-001：只注册一个 `lsp` 工具

决定：所有语言和操作共用一个带 `operation` 参数的工具。

原因：减少工具说明占用的上下文，统一 `/tools` 开关、失败处理和输出格式。

### ADR-002：使用标准 JSON-RPC 和 LSP 类型

决定：使用 `vscode-jsonrpc` 和 `vscode-languageserver-protocol`，不自行发明协议或手写消息分帧。

原因：LSP 的消息边界、取消、服务端请求和错误语义已有标准实现。复用标准库比自定义传输更可靠。

### ADR-003：TypeScript/JavaScript 随 Pi 提供

决定：固定依赖 `typescript-language-server` 和 `typescript`；独立 Bun 二进制无法把自身当作 JavaScript 运行时，因此改为寻找 PATH 中的服务器并给出安装提示。

原因：当前项目主要使用 TypeScript；核心能力不能要求用户先研究和安装额外程序。

### ADR-004：Python 和 Go 使用本机标准服务器

决定：Python 自动寻找 basedpyright、pyright 或 pylsp；Go 寻找 gopls。

原因：这些服务器依赖对应语言环境和项目配置。Pi 负责协议兼容和清楚提示，不在 Node 包里偷偷安装 Python 或 Go 工具链。

### ADR-005：直接启动进程，不执行用户 Shell 命令

决定：使用 `cross-spawn` 且 `shell: false` 启动语言服务器。

原因：LSP 服务器是受控子进程，不是终端脚本。这样不依赖 Bash、PowerShell 或 WSL 的语法与配置。

### ADR-006：懒启动并按工作区复用

决定：只有第一次调用时启动；同一语言工作区后续复用。

原因：启动和项目分析有成本，但重复启动更慢。未使用 LSP 的任务不承担成本。

### ADR-007：失败开放并缓存终止错误

决定：缺少服务器、启动失败和损坏连接会产生简短回退提示；同一会话不重复启动同一失败目标。

原因：LSP 是准确性增强工具，不能成为完成任务的硬依赖，也不能像早期语义搜索一样重复消耗时间。

### ADR-008：所有写入限制在当前项目

决定：只允许 `rename` 修改 Pi 当前工作目录内部的普通文件。

原因：语言服务器可能返回依赖、缓存或外部工作区路径。代理不能借重命名越过用户给定的项目范围。

### ADR-009：结果默认紧凑

决定：位置结果去重、排序并限制数量；诊断和符号只返回必要字段。

原因：LSP 可以返回数百条引用。默认倾倒全部结果会抵消它节省搜索和读取 Token 的价值。

### ADR-010：在工具批次结束后执行有界增量诊断

状态：已接受。

决定：成功的 `edit`、`write` 和 `lsp rename` 记录修改路径后，立即在后台预热对应语言服务器并打开该文件，正式诊断仍在 `turn_end` 统一执行。冷启动尚未完成时允许延后一回合，让启动与模型工作并行；同一批文件只延后一次。每批最多检查 8 个文件、等待 2500ms、向模型反馈 20 条问题；同一次代理运行最多反馈两轮。语言服务器本轮刚启动且首次返回空结果时，只对该文件确认一次，确认仍受同一个 2500ms 总预算限制。无问题时不写入模型上下文，失败时开放降级。

正面影响：多个连续编辑仍只正式检查一次；冷启动时间与模型工作重叠；正常情况下没有额外模型 Token；错误能进入后续修复回合；语言服务器异常不会拖垮任务。

负面影响：冷启动时诊断反馈可能比正常情况晚一个回合；第一次启动在延后一回合后仍超过总预算时会跳过；只检查修改文件会漏掉未打开文件中的部分项目级错误；两轮上限后需要代理主动运行项目检查。

替代方案：每次编辑后立即检查会重复等待；在代理结束后检查无法自动修复；全项目检查更完整，但速度和输出不可控。因此选择 `turn_end` 的有界增量检查，最终正确性仍交给项目自己的检查和测试。

### ADR-011：项目级检查复用 `lsp diagnostics`，不新增工具

状态：已接受。

决定：`diagnostics path="*"` 根据当前目录标记运行 TypeScript、Python 或 Go 的标准检查命令。命令直接启动且参数固定，默认超时 20 秒，输出默认限制 50 行。它不会自动运行，也不替代项目测试。

原因：单文件语言诊断和项目类型检查都回答“代码是否存在语言级问题”。放进同一个工具可以减少工具数量和提示词占用，避免模型在 `lsp` 与独立 `check` 之间选错。

替代方案：独立 `check` 工具边界重复；让模型使用 `bash` 容易选错命令、产生冗长输出或再次触发 Windows shell 问题；自动在每次修改后运行全项目检查会明显拖慢任务。因此选择一个明确调用、固定命令、有界输出的项目诊断入口。

## 测试要求

- 三种语言的文件识别、根目录和服务器选择。
- 标准 initialize、文档同步、超时和关闭流程。
- 位置的 1/0 基转换和 UTF-16 字符索引。
- 每项只读操作的请求和紧凑输出。
- 符号唯一、缺失和歧义处理。
- 客户端复用、启动失败缓存和会话清理。
- 自动诊断的修改文件收集、后台预热、单次延后、批处理、冷启动空结果确认、结果上限、超时降级和两轮熔断。
- 项目类型识别、固定命令选择、Python 回退、Go 工作区展开、超时、缺失命令和输出截断。
- rename 的多文件编辑、项目边界、重叠检测和失败回滚。
- 真实 TypeScript 服务器的定义、诊断和重命名冒烟测试。
- 类型定义、代码操作预览与应用、文件重命名、状态、重载、能力查询和受控请求。
